ENROLLING A CLIENT

Nothing works until a client enrolls. The enrollment token is not a request
credential — it is used once, in a browser, and exchanged for tokens scoped to a
single named session that can be revoked on its own.

  1. Point your MCP client at {{ .Values.publicURL }}/mcp
  2. It gets a 401 and discovers the authorization server automatically.
  3. It opens a browser at {{ .Values.publicURL }}/oauth/authorize
  4. Paste the enrollment token and name the session.

To read the token you deployed with:

  kubectl -n {{ .Release.Namespace }} get secret {{ include "whois-mcp.secretName" . }} \
    -o jsonpath='{.data.{{ .Values.secrets.enrollmentTokenKey }}}' | base64 -d; echo

Give each client its own session by enrolling each one separately. That is what
makes "cut off that one client" answerable later:

  session_list     (needs the whois:admin scope)
  session_revoke   (needs the whois:admin scope)

SCOPES

  whois:read   lookups                              (advertised, granted by default)
  whois:raw    unredacted raw RDAP and WHOIS text    (step-up)
  whois:admin  list and revoke sessions             (step-up)

Only whois:read is advertised in the metadata. A client that never asks for more
never holds a credential that can dump contact data.

ROTATING THE SIGNING KEY

See deploy/helm/whois-mcp/RUNBOOK_KEY_ROTATION.md. The short version: publish the
new key alongside the old, wait one access-token lifetime (10 minutes), then
retire the old one. Retiring it early invalidates tokens that are still valid.
